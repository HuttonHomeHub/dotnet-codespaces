# Deploying PhotoMapper with Docker Compose

Every push to `main` runs the **Containers** workflow (`.github/workflows/deploy.yml`), which:

1. builds the `apiservice` and `web` images (chiseled Ubuntu, non-root) with `dotnet publish -t:PublishContainer`;
2. generates `docker-compose.yaml` from the AppHost with `aspire publish`;
3. starts that stack behind the Caddy proxy and smoke-tests it (`smoke-test.sh`);
4. pushes the tested images to `ghcr.io/huttonhomehub/photomapper-{apiservice,web}` (tags `sha-<commit>` and `latest`) with signed build provenance;
5. uploads a **deployment bundle** artifact, `deploy-bundle-<commit>`, kept for 90 days.

Pull requests run steps 1–3 only.

## What's in the bundle

| File | Source | Purpose |
|---|---|---|
| `docker-compose.yaml` | generated by `aspire publish` | API, web app and Aspire dashboard |
| `.env` | generated by `write-env.sh` | Image references pinned by digest, container ports |
| `compose.proxy.yaml`, `Caddyfile` | this folder | Caddy reverse proxy: HTTPS with automatic Let's Encrypt certificates |
| `site.env.example` | this folder | Template for the server-specific `site.env` |

Only the proxy publishes ports (80 and 443). The web app and API are reachable only on the internal Docker network, and the dashboard only on the server's loopback interface.

## One-time server setup

1. Install Docker Engine with the Compose plugin.
2. Point a DNS record (for example `photos.example.com`) at the server and open ports 80 and 443 (TCP and UDP).
3. Make sure the server can pull the images. Either:
   - make the two `photomapper-*` packages public (GitHub → your profile → Packages → package → Package settings → Change visibility), or
   - run `docker login ghcr.io` on the server with a personal access token that has only `read:packages`.
4. Create a directory for the app (for example `/opt/photomapper`) and, in it, a `site.env` from `site.env.example` with `SITE_ADDRESS` set to your hostname.

## Deploy or update

From a machine with the GitHub CLI, fetch the bundle for the commit you want (the latest run on `main` by default):

```bash
gh run download --repo HuttonHomeHub/dotnet-codespaces --name deploy-bundle-<commit> --dir bundle
scp -r bundle/. server:/opt/photomapper/        # keeps the existing site.env
```

Then on the server:

```bash
cd /opt/photomapper
docker compose --env-file .env --env-file site.env -f docker-compose.yaml -f compose.proxy.yaml pull
docker compose --env-file .env --env-file site.env -f docker-compose.yaml -f compose.proxy.yaml up -d --remove-orphans
```

**Rollback:** deploy the bundle from an earlier commit the same way. Images are pinned by digest, so this restores exactly what that commit shipped.

## Operating

- **Dashboard (logs, traces, metrics):** `ssh -L 18888:localhost:18888 server`, then open <http://localhost:18888>. The login token is in `docker compose ... logs compose-dashboard`. Telemetry is kept in memory and lost when the dashboard restarts.
- **State worth backing up:** the `caddy_data` volume (certificates) and the `webfrontend-home` volume (ASP.NET Core data protection keys; losing them signs users out and invalidates open forms).
- **Health:** containers restart automatically (`unless-stopped`). There are no Compose health checks, because the chiseled images have no shell or `curl`, and the app's `/health` endpoints are only mapped in Development.

## Testing a bundle locally

```bash
aspire publish -o deploy/out
cp deploy/compose.proxy.yaml deploy/Caddyfile deploy/out/
for p in ApiService Web; do dotnet publish src/PhotoMapper.$p -c Release -t:PublishContainer -p:ContainerImageTags=ci; done
deploy/write-env.sh deploy/out huttonhomehub/photomapper-apiservice:ci huttonhomehub/photomapper-web:ci
deploy/smoke-test.sh deploy/out
```
