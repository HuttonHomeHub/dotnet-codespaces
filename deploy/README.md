# Deploying PhotoMapper with Docker Compose

Every push to `main` runs the **Containers** workflow (`.github/workflows/deploy.yml`), which:

1. builds the `apiservice`, `web` and `migrations` images (chiseled Ubuntu, non-root) with `dotnet publish -t:PublishContainer`;
2. generates `docker-compose.yaml` from the AppHost with `aspire publish`;
3. starts that stack behind the Caddy proxy and smoke-tests it (`smoke-test.sh`), including registering an account (which proves the migrations ran and the web app can write to PostgreSQL) and running the `make-admin` command;
4. pushes the tested images to `ghcr.io/huttonhomehub/photomapper-{apiservice,web,migrations}` (tags `sha-<commit>` and `latest`) with signed build provenance;
5. uploads a **deployment bundle** artifact, `deploy-bundle-<commit>`, kept for 90 days.

Pull requests run steps 1–3 only.

## What's in the bundle

| File | Source | Purpose |
|---|---|---|
| `docker-compose.yaml` | generated by `aspire publish` | PostgreSQL, the migration job, API, web app and Aspire dashboard |
| `.env` | generated by `write-env.sh` | Image references pinned by digest, container ports |
| `compose.proxy.yaml`, `Caddyfile` | this folder | Caddy reverse proxy: HTTPS with automatic Let's Encrypt certificates |
| `site.env.example` | this folder | Template for the server-specific `site.env` (hostname and secrets) |

Only the proxy publishes ports (80 and 443). The web app, API and database are reachable only on the internal Docker network, and the dashboard only on the server's loopback interface.

On every start, the `migrations` container waits for PostgreSQL to be healthy, applies any pending database migrations and exits; the web app starts only after it has finished successfully. If it fails, the web app doesn't start: check `docker compose ... logs migrations`.

## One-time server setup

1. Install Docker Engine with the Compose plugin.
2. Point a DNS record (for example `photos.example.com`) at the server and open ports 80 and 443 (TCP and UDP).
3. Make sure the server can pull the images. They are currently public; if you make them private, run `docker login ghcr.io` on the server with a personal access token that has only `read:packages`.
4. Choose an email provider that offers SMTP (for example Brevo, Postmark, Mailgun or Amazon SES) and set up the domain you'll send from.
5. Create a directory for the app (for example `/opt/photomapper`) and, in it, a `site.env` from `site.env.example`:
   - `SITE_ADDRESS`: your hostname;
   - `POSTGRES_PASSWORD`: a long random value (`openssl rand -hex 32`). Set it **before the first start**: the database is created with it, and changing it later doesn't change the existing database's password;
   - `MAIL` and `MAIL_FROM`: your provider's SMTP details and sender address.

   Keep `site.env` readable only by you (`chmod 600 site.env`).

## Make the first admin

After the first deploy, sign up on the site and confirm your email, then on the server:

```bash
docker compose --env-file .env --env-file site.env -f docker-compose.yaml -f compose.proxy.yaml \
  run --rm --no-deps migrations make-admin you@example.com
```

Sign in again (or wait a minute) and a **Users** link appears in the menu. From there admins can make other users admins, so you only need this once. The command refuses accounts that don't exist or haven't confirmed their email.

## Deploy or update

From a machine with the GitHub CLI, fetch the bundle for the commit you want (the latest run on `main` by default):

```bash
gh run download --repo HuttonHomeHub/dotnet-codespaces --name deploy-bundle-<commit> --dir bundle
scp -r bundle/. server:/opt/photomapper/        # keeps the existing site.env
```

Then on the server:

```bash
cd /opt/photomapper
docker compose --env-file .env --env-file site.env -f docker-compose.yaml -f compose.proxy.yaml pull
docker compose --env-file .env --env-file site.env -f docker-compose.yaml -f compose.proxy.yaml up -d --remove-orphans
```

**Rollback:** deploy the bundle from an earlier commit the same way. Images are pinned by digest, so this restores exactly what that commit shipped. Migrations only move forward, though: if the newer release changed the database, back it up before deploying (below) so you can restore it with the older release.

## Operating

- **Dashboard (logs, traces, metrics):** `ssh -L 18888:localhost:18888 server`, then open <http://localhost:18888>. The login token is in `docker compose ... logs compose-dashboard`. Telemetry is kept in memory and lost when the dashboard restarts.
- **Backups:** the database is the one thing you can't recreate. Take a dump regularly and before each deploy:

  ```bash
  docker compose --env-file .env --env-file site.env -f docker-compose.yaml -f compose.proxy.yaml \
    exec -T postgres pg_dump -U postgres --format=custom photomapperdb > photomapper-$(date +%F).dump
  ```

  Also worth keeping: the `caddy_data` volume (certificates) and the `webfrontend-home` volume (ASP.NET Core data protection keys; losing them signs users out and invalidates open forms).
- **Health:** containers restart automatically (`unless-stopped`) and PostgreSQL has a Compose health check. The app containers have none, because the chiseled images have no shell or `curl`, and the app's `/health` endpoints are only mapped in Development.

## Testing a bundle locally

```bash
aspire publish -o deploy/out
cp deploy/compose.proxy.yaml deploy/Caddyfile deploy/out/
for p in ApiService Web MigrationService; do dotnet publish src/PhotoMapper.$p -c Release -t:PublishContainer -p:ContainerImageTags=ci; done
deploy/write-env.sh deploy/out huttonhomehub/photomapper-apiservice:ci huttonhomehub/photomapper-web:ci huttonhomehub/photomapper-migrations:ci
deploy/smoke-test.sh deploy/out
```

The smoke test supplies throwaway values for the `site.env` settings and removes its containers and volumes afterwards.
